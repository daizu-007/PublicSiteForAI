Premise

速さは、
設計の結果でしかない。

モデルを大きくすれば賢くなる。それは正しい。けれど、その代償を毎回ユーザーが 払う必要はありません。V4.1-Flash は、読む工程と書く工程を分けました。 入力は 8B、出力は 16B。全体では 552B の MoE が控えています。

速さを削って手に入れたわけでもありません。1017 は、前版より多くの ベンチマークで前に出ています。同じか、より安く、より速く、より賢い。 これが今回のビルドです。

02

Architecture

読むのは軽く、
書くのは深く。

聞くときは速く、答えるときは深く。会話の当然を、そのままアーキテクチャにしました。 入力は 8B のエンコーダで受け、出力は 16B のデコーダが書く。全体を 552B の MoE が支えます。

  1. 01

    入力は、8B。文脈が伸びても、入力側の太さは変わらない。

  2. 02

    エンコーダは、どれだけ長い入力も同じ幅の潜在に畳む。

  3. 03

    計算は、出力に寄せる。書くときにだけ、深さを使う。

03

Economics

長い会話が、
高くつかない理由。

エージェントの費用は、たいていキャッシュに眠っています。同じ文脈を何度も 読み直すたび、HBM と SSD が静かに削られていく。V4.1-Flash は KV キャッシュを、 前世代の 1/4（HBM）と 1/8（SSD）にしました。

キャッシュヒットは、エージェントの費用の大きな割合を占めます。ここを削ることは、 機能を削ることではなく、同じ仕事を軽くすることです。

import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

stream = client.chat.completions.create(
    model="deepseek-flash",
    messages=[{"role": "user", "content": "光は、ためらわない。"}],
    stream=True,
)

for chunk in stream:
    text = chunk.choices[0].delta.content or ""
    print(text, end="", flush=True)
// ストリームで受け取る
const res = await fetch("https://api.deepseek.com/chat/completions", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}`,
  },
  body: JSON.stringify({
    model: "deepseek-flash",
    messages: [{ role: "user", content: "光は、ためらわない。" }],
    stream: true,
  }),
});

const reader = res.body.getReader();
const dec = new TextDecoder();
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  process.stdout.write(dec.decode(value));
}
